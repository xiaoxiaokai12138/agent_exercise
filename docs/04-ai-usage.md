协作中最重要的检查点是模型结论与工具事实能否对应。真实模型的一次早期运行中，审核工具已返回 `pass`，时段工具随后返回 `conflict`，模型却选择 `finish_blocked`，并把原因写成审核风险。仅检查输出 JSON 是否合法，仍可能放过业务语义错误。开发阶段据此调整提示词，突出最近观察，明确区分审核风险和排期冲突，并让执行器校验结束结论的依据。该问题的发现、修改和复跑由 Codex 辅助执行，具体过程见复盘文档。[早期误判 Trace](../examples/runs/initial/conflict-v2.trace.json) · [修正后的 Trace](../examples/runs/ollama/conflict.trace.json) · [复盘](05-retrospective.md)

还出现过动作与终态相互矛盾的问题。初版响应允许同时返回 `action` 和 `outcome`，调试时模型在选择 `save_draft` 时提前填入完成结果。修改后，每轮使用一个动作枚举，保存成功后才能选择 `finish_done`。执行器仍需要核对 `saved` 或 `reused` 的实际观察，模型的一句“完成”不足以形成成功结果。[首轮失败 Trace](../examples/runs/initial/normal.trace.json) · [正常完成 Trace](../examples/runs/ollama/normal.trace.json)

下面的人工复核与返修演练基于已经出现的冲突误判，以及现有自动化测试中的不安全动作模拟。

假设人工复核时看到一个看似合理的 AI 建议，“18:00 已占用，19:00 可用，可以直接保存 19:00 的草稿”。这一步需要回到原请求检查授权。用户只要求 18:00，工具查到的备选仅证明 19:00 可用。人工应提出返修条件，保留原时间要求，将 19:00 放入待确认项，并检查保存工具最终收到的参数。这个演练中的直接改期建议为假设输入；真实早期 Trace 中出现的错误是把冲突误判为审核风险。

以下按当前实现整理六步复核路径。

1. 使用 `examples/inputs/schedule.json` 中 M01 的 18:00 请求，配合 `data/schedule_busy.json`。审核工具返回 `state=pass`，时段查询返回 `state=conflict`、`source=existing_schedule`。备选时段由另一次 `find_alternatives` 调用返回。

2. 对照失败与修正后的 Trace。早期真实错误是模型在冲突后选择 `finish_blocked`，与审核通过的观察矛盾。修正后模型选择 `find_alternatives`，得到 `slots=["2026-11-09T19:00"]`，再结束为待确认。原始失败记录中没有发生将 19:00 写入草稿的动作。

3. 使用 `rg -n "save_draft|requested_at|last_slot" src` 定位调用点。在 `src/agent.py::tool_arguments` 中，保存参数取自原请求的 `requested_at`，还要求审核通过及原时段可用的观察。当前模型仅返回动作和简短理由，保存时段由执行器绑定。

4. 核对冲突用例的 JSON 输出。`pending_confirmation.slots` 含 19:00，`requested_at` 仍为 18:00，`draft.state=not_attempted`。SQLite 只有 `drafts` 业务表，冲突场景新增零条。请求和待确认项保存在 JSON 输出中。

5. 使用 `examples/inputs/confirmed.json` 显式提交 19:00，并复用冲突场景的数据库。系统把它作为新的授权请求，重新审核并查询时段，再由保存工具复核静态排期及数据库占用。成功输出 `draft.state=saved`。此时新请求的时间为 19:00，早先的 18:00 请求记录仍可从原输出核对。

6. 运行不安全动作测试与案例复跑。冲突后直接调用 `save_draft` 会得到 `guard_rejected` 和 `missing_tool_precondition`；没有保存依据便选择 `finish_done` 会得到 `guard_rejected` 和 `unsupported_finish`。案例复跑检查业务状态、数据库行数、重复草稿 ID 和关键动作。新建草稿的 ID 会变化，结果按验收断言比较。

现有测试已经覆盖上述保存保护逻辑。自动化测试入口为 `python -X utf8 -m unittest discover -s tests -v`。案例入口分别为 `python -X utf8 examples/reproduce.py --mode mock` 和 `python -X utf8 examples/reproduce.py --mode ollama`。真实模式依赖本地 Ollama 服务和模型。[测试代码](../tests/test_agent.py) · [测试结果](../examples/test-results.txt)
